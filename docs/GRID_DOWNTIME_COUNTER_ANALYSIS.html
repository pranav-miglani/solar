Executive Summary

This document analyzes the requirements and design for implementing a cumulative grid downtime counter system, similar to how total energy is tracked. The system will maintain per plant:

  • Daily grid downtime counter (100-day rolling retention, resets daily)
  • Total grid downtime counter (monotonically increasing, never resets)
Key Requirement: Grid downtime must be calculated for both closed/resolved alerts AND open alerts. Open alerts contribute downtime from alert_time to current time (NOW()).

Current State Analysis

1. Current Grid Downtime Tracking

Location: alerts table

  • grid_down_seconds (INTEGER) - Duration of each alert in seconds
  • grid_down_benefit_kwh (NUMERIC(12,3)) - Calculated benefit energy

Calculation:

  • grid_down_seconds = max(0, end_time - alert_time)
  • grid_down_benefit_kwh = 0.5 × hours(9AM-4PM overlap) × capacity_kw
Characteristics:
  • ✓ Per-alert granularity (individual alert records)
  • ✓ Calculated during alert sync
  • ✗ No cumulative aggregation
  • ✗ No time-series tracking
  • ✗ No daily/monthly/total counters

2. Reference Pattern: Energy Counters

Main DB (plants table):

  • daily_energy_kwh - Current day's energy
  • monthly_energy_mwh - Month-to-date energy
  • yearly_energy_mwh - Year-to-date energy
  • total_energy_mwh - Cumulative total (monotonically increasing)

Analytics DB (plant_energy_readings table):

  • Daily snapshots with 100-day retention
  • Columns: daily_energy_kwh, monthly_energy_kwh, yearly_energy_mwh, total_energy_mwh
  • Unique constraint: (plant_id, reading_date)
  • Cleanup function: Deletes records older than 100 days

Sync Mechanism:

  • Updated during telemetry sync (every 15 minutes)
  • Snapshot captured daily at 10 PM IST via analyticsSnapshotService.ts
  • Values come directly from vendor API (not aggregated from alerts)

Requirements Analysis

Functional Requirements

  1. Daily Counter: Grid downtime accumulated per day (100-day retention, resets daily at midnight IST)
  2. Total Counter: Cumulative grid downtime (monotonically increasing, never resets)
  3. Per Plant Basis: Counters maintained separately for each plant
  4. Open Alerts Support: Calculate downtime for open alerts (from alert_time to NOW())
  5. Closed Alerts Support: Calculate downtime for closed alerts (from alert_time to end_time)
  6. Aggregation Source: Aggregate from alerts table (not vendor API)

Non-Functional Requirements

  1. Performance: Efficient aggregation queries
  2. Data Integrity: Accurate cumulative calculations
  3. Retention: 100-day rolling window for daily snapshots, total counter never resets
  4. Consistency: Counters should match sum of alerts

2. Counter Calculation Logic

Key Challenge: Open alerts don't have end_time, so we need to calculate downtime from alert_time to NOW(). This means counters need periodic recalculation.

Option A: Recalculate on Every Alert Sync (Simple but Less Efficient)

During Alert Sync (alertSyncService.ts)

TypeScript - Recalculate All Counters
// After syncing all alerts for a plant, recalculate counters
async function recalculatePlantDowntimeCounters(plantId: number) {
  const now = new Date();
  const todayStart = new Date(now);
  todayStart.setHours(0, 0, 0, 0);
  
  // Get all alerts for this plant
  const { data: alerts } = await supabase
    .from("alerts")
    .select("alert_time, end_time, grid_down_seconds, grid_down_benefit_kwh")
    .eq("plant_id", plantId);
  
  let dailySeconds = 0;
  let totalSeconds = 0;
  let dailyBenefit = 0;
  let totalBenefit = 0;
  
  for (const alert of alerts || []) {
    let alertSeconds = 0;
    
    if (alert.end_time) {
      // Closed alert: use stored grid_down_seconds
      alertSeconds = alert.grid_down_seconds || 0;
    } else {
      // Open alert: calculate from alert_time to NOW()
      const alertTime = new Date(alert.alert_time);
      alertSeconds = Math.floor((now.getTime() - alertTime.getTime()) / 1000);
    }
    
    totalSeconds += alertSeconds;
    totalBenefit += alert.grid_down_benefit_kwh || 0;
    
    // Check if alert overlaps with today
    const alertTime = new Date(alert.alert_time);
    const alertEnd = alert.end_time ? new Date(alert.end_time) : now;
    
    if (alertEnd >= todayStart) {
      const overlapStart = alertTime > todayStart ? alertTime : todayStart;
      const overlapEnd = alertEnd < now ? alertEnd : now;
      const overlapSeconds = Math.floor((overlapEnd.getTime() - overlapStart.getTime()) / 1000);
      dailySeconds += Math.max(0, overlapSeconds);
    }
  }
  
  // Update plant counters
  await supabase
    .from("plants")
    .update({
      daily_grid_down_seconds: dailySeconds,
      total_grid_down_seconds: totalSeconds,
      daily_grid_down_benefit_kwh: dailyBenefit,
      total_grid_down_benefit_kwh: totalBenefit,
      last_open_alert_calc_at: now.toISOString(),
    })
    .eq("id", plantId);
}

Option B: Incremental Updates + Periodic Recalculation (Optimized)

Recommended Approach:

  1. During Alert Sync: Only recalculate for plants with new/updated alerts
  2. Periodic Cron: Recalculate open alerts every 15 minutes for all plants
  3. Daily Snapshot: Full recalculation before snapshot
Important Considerations:
  • Open Alerts: Must recalculate periodically (every 15 minutes recommended)
  • Daily Counter: Needs full recalculation to handle day boundaries correctly
  • Total Counter: Can use incremental updates for closed alerts, but open alerts need recalculation
  • Performance: Recalculating all alerts per plant is O(n) where n = number of alerts. For plants with many alerts, consider batching or caching.

3. Daily Snapshot Logic

New Service: lib/services/gridDowntimeSnapshotService.ts

Similar to analyticsSnapshotService.ts, but for grid downtime:

  1. Fetch all plants from main DB
  2. For each plant:
    • Recalculate all counters (including open alerts up to NOW())
    • Upsert into plant_grid_downtime_readings (analytics DB)
    • Reset daily_grid_down_seconds = 0 in main DB
    • Keep total_grid_down_seconds (never resets)
  3. Call cleanup function (delete records older than 100 days)

5. Optimization Strategies

Strategy 1: Smart Recalculation (Recommended)

Only recalculate when necessary:

  • During Alert Sync: Recalculate only for plants with new/updated alerts
  • Periodic Cron: Only recalculate plants with open alerts (use last_open_alert_calc_at index)
  • Daily Snapshot: Full recalculation for all plants (ensures accuracy)
SQL Query - Find Plants Needing Recalculation
-- Find plants with open alerts that need recalculation
SELECT DISTINCT p.id, p.name
FROM plants p
INNER JOIN alerts a ON a.plant_id = p.id
WHERE a.end_time IS NULL  -- Open alerts
  AND (
    p.last_open_alert_calc_at IS NULL
    OR p.last_open_alert_calc_at < NOW() - INTERVAL '15 minutes'
  )
ORDER BY p.id;

Strategy 2: Batch Processing

Process plants in batches to avoid timeouts:

  • Process 100 plants at a time
  • Use Promise.all with concurrency limit (e.g., 10 concurrent plants)
  • Log progress for monitoring

Strategy 3: Caching Open Alert Calculations

Cache calculations with TTL:

  • Store calculated downtime for open alerts in memory/Redis
  • TTL: 15 minutes (matches cron frequency)
  • Invalidate cache when alert is updated/resolved
Trade-off: Caching adds complexity but reduces database load. For most use cases, direct recalculation is simpler and sufficient.

Strategy 4: Database-Level Calculation (Advanced)

Use PostgreSQL functions to calculate in-database:

SQL Function - Calculate Plant Downtime
CREATE OR REPLACE FUNCTION calculate_plant_downtime(
  p_plant_id INTEGER,
  p_calc_time TIMESTAMPTZ DEFAULT NOW()
)
RETURNS TABLE(
  daily_seconds INTEGER,
  total_seconds INTEGER,
  daily_benefit_kwh NUMERIC,
  total_benefit_kwh NUMERIC
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_today_start TIMESTAMPTZ;
  v_daily_seconds INTEGER := 0;
  v_total_seconds INTEGER := 0;
  v_daily_benefit NUMERIC := 0;
  v_total_benefit NUMERIC := 0;
BEGIN
  v_today_start := DATE_TRUNC('day', p_calc_time AT TIME ZONE 'Asia/Kolkata') AT TIME ZONE 'Asia/Kolkata';
  
  SELECT 
    COALESCE(SUM(
      CASE 
        WHEN end_time IS NOT NULL THEN 
          EXTRACT(EPOCH FROM (end_time - alert_time))::INTEGER
        ELSE 
          EXTRACT(EPOCH FROM (p_calc_time - alert_time))::INTEGER
      END
    ), 0),
    COALESCE(SUM(
      CASE 
        WHEN end_time IS NOT NULL THEN 
          CASE 
            WHEN end_time >= v_today_start AND alert_time < p_calc_time THEN
              EXTRACT(EPOCH FROM (LEAST(end_time, p_calc_time) - GREATEST(alert_time, v_today_start)))::INTEGER
            ELSE 0
          END
        ELSE 
          CASE 
            WHEN alert_time < p_calc_time THEN
              EXTRACT(EPOCH FROM (p_calc_time - GREATEST(alert_time, v_today_start)))::INTEGER
            ELSE 0
          END
      END
    ), 0),
    COALESCE(SUM(grid_down_benefit_kwh), 0),
    COALESCE(SUM(
      CASE 
        WHEN end_time >= v_today_start OR (end_time IS NULL AND alert_time < p_calc_time) THEN
          grid_down_benefit_kwh
        ELSE 0
      END
    ), 0)
  INTO v_total_seconds, v_daily_seconds, v_total_benefit, v_daily_benefit
  FROM alerts
  WHERE plant_id = p_plant_id;
  
  RETURN QUERY SELECT 
    GREATEST(0, v_daily_seconds)::INTEGER,
    GREATEST(0, v_total_seconds)::INTEGER,
    GREATEST(0, v_daily_benefit)::NUMERIC,
    GREATEST(0, v_total_benefit)::NUMERIC;
END;
$$;
Recommendation: Use Strategy 1 (Smart Recalculation) for initial implementation. It's simple, efficient, and maintainable. Consider Strategy 4 (Database Functions) if performance becomes an issue with large numbers of alerts.

Data Flow Summary

Alert Sync Flow (Every Hour)

  1. Fetch alerts from vendor API
  2. For each alert:
    • Calculate grid_down_seconds and grid_down_benefit_kwh
      • If end_time exists: end_time - alert_time
      • If end_time is NULL: NOW() - alert_time (open alert)
    • Upsert alert into alerts table
  3. For each affected plant (with new/updated alerts):
    • Recalculate all counters (sum all alerts for that plant)
    • Update daily_grid_down_seconds and total_grid_down_seconds
    • Update last_open_alert_calc_at = NOW()

Periodic Recalculation Flow (Every 15 Minutes)

  1. Find plants with open alerts that need recalculation:
    • Query plants where last_open_alert_calc_at is NULL or older than 15 minutes
    • Join with alerts table to find plants with open alerts (end_time IS NULL)
  2. For each plant:
    • Recalculate all counters (including open alerts up to NOW())
    • Update daily_grid_down_seconds and total_grid_down_seconds
    • Update last_open_alert_calc_at = NOW()

Daily Snapshot Flow (10 PM IST)

  1. For each plant:
    • Recalculate all counters (full recalculation including open alerts)
    • Read current counters from plants table
    • Upsert into plant_grid_downtime_readings (analytics DB)
    • Reset daily_grid_down_seconds = 0 (keep total_grid_down_seconds)
  2. Call cleanup function (delete records older than 100 days)

Cost & Performance Considerations

Database Storage

Main DB (plants table):

  • 4 new columns (2 INTEGER + 2 NUMERIC) + 1 TIMESTAMPTZ ≈ 32 bytes per plant
  • For 10,000 plants: ~320 KB (negligible)

Analytics DB (plant_grid_downtime_readings table):

  • ~150 bytes per record (with indexes)
  • 10,000 plants × 100 days = 1,000,000 records
  • Total: ~150 MB (well within free tier)

Query Performance

  • Counter Recalculation: O(n) where n = number of alerts per plant (requires full scan of alerts)
  • Periodic Recalculation: O(m × n) where m = plants with open alerts, n = alerts per plant
  • Snapshot: O(p × n) where p = total plants, n = average alerts per plant
  • Historical Queries: O(log n) with proper indexes
Performance Considerations:
  • Plants with many alerts (100+) may take 100-500ms to recalculate
  • Periodic recalculation should process plants in batches (100 at a time)
  • Consider database-level calculation (SQL function) for better performance
  • Monitor query execution time and add indexes if needed

Impact on Alert Sync

  • Additional Queries: 1 recalculation per affected plant (not per alert)
  • Performance Impact: Moderate (recalculation requires scanning all alerts for plant)
  • Latency: +50-200ms per affected plant (depends on number of alerts)
  • Optimization: Only recalculate plants with new/updated alerts

Conclusion

The recommended approach (Option 1: Dual Storage) provides:

  • ✓ Consistent with existing energy counter pattern
  • ✓ Fast current value queries (main DB)
  • ✓ Historical trend analysis (analytics DB)
  • ✓ 100-day retention for daily snapshots
  • ✓ Total counter never resets (monotonically increasing)
  • ✓ Support for both open and closed alerts
  • ✓ Optimized recalculation (only when needed)
  • ✓ Simplified design (only 2 counters: daily and total)

This design maintains consistency with the existing architecture while providing the required functionality for grid downtime tracking. The simplified approach (daily + total only) reduces complexity while still providing all necessary insights.

Principal Engineer Recommendations

  1. Start Simple: Implement Strategy 1 (Smart Recalculation) first. It's maintainable and sufficient for most use cases.
  2. Monitor Performance: Track recalculation times. If plants with 100+ alerts take >500ms, consider Strategy 4 (Database Functions).
  3. Batch Processing: Always process plants in batches (100 at a time) to avoid timeouts and memory issues.
  4. Index Optimization: Ensure indexes on alerts(plant_id, alert_time, end_time) for fast recalculation queries.
  5. Error Handling: Implement retry logic for failed recalculations. Log errors but don't block alert sync.
  6. Testing: Test with plants that have 0, 1, 10, 100, and 1000+ alerts to validate performance.
  7. Gradual Rollout: Deploy to staging first, monitor for 1 week, then production with feature flag.
